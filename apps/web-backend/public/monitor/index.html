Project case study · personal, full-stack

Monitoring Platform

A full-stack system for monitoring Android devices in real time: a React dashboard, an Expo mobile app, and a small backend monorepo built around one deliberate split — live delivery to a dashboard never waits on a database write, and a database write never waits on live delivery. This page walks through how it's built, the trade-offs made on purpose, and how to try the companion desktop app.

01 — Orientation

What it is, and why it's worth a look

A SaaS product for organizations that need to monitor a fleet of Android devices — kiosks, handheld scanners, point-of-sale phones — across multiple sites.

An admin creates an account, which provisions a tenant with a workspace/location hierarchy; from the dashboard they generate a QR pairing code scoped to a location, a phone scans it, and that device starts streaming live battery/memory/disk/CPU stats to a Monitor page in real time. Role-based access controls who can see or manage which devices, at which sites, across the organization.

  • Full-stack across four platforms — a React web dashboard, an Expo/React Native mobile app, a Nest + plain-TypeScript backend (its own four-process monorepo), and a standalone Electron desktop app with its own auto-built, auto-released installers.
  • A real event-streaming pipeline, not just CRUD — device metrics flow through Kafka to two consumer groups with opposite scaling semantics from the same topic: a shared group that shards partitions across instances for durable writes, and a per-process group that broadcasts a full copy of the stream for in-memory dashboard fan-out.
  • A deliberate availability/consistency split — live delivery to a dashboard never waits on a database write, and that write never waits on live delivery either. Two independent paths to the same data, on purpose.
My role. Sole engineer end to end — designed the multi-service backend split (API, WebSocket, ingestion worker, cron worker) sharing common auth/database packages in an npm-workspace monorepo; built the QR-code pairing flow and real-time device dashboard in React; set up AWS ECS/ECR deployment through GitHub Actions using OIDC (no long-lived AWS credentials in CI); and packaged the companion Electron app for Windows (NSIS) and Linux (AppImage) behind a tag-triggered release pipeline.

02 — Orientation

System map

Two clients (web dashboard, mobile app) talk to a four-process backend. Kafka sits between the WebSocket layer and its two independent consumers. Redis and ClickHouse are provisioned but idle; the desktop app doesn't connect to any of this at all.

03 — Identity

Auth & access scope

JWT access + refresh tokens identify who; a three-level scope hierarchy decides what they can touch. A role assignment made at a higher level automatically covers everything nested beneath it.

Two token scopes, never interchangeable. A user-scoped token (issued at login) is required on /ws/dashboard/*; a device-scoped token (issued at pairing claim) is required on /ws/device/*. Each socket rejects the other token type outright.

04 — Onboarding

Device pairing

A short-lived, location-scoped code links an unauthenticated phone to an authenticated dashboard session — the phone never sees the user's own credentials.

05 — The core mechanism

Live metrics pipeline

One Kafka topic, keyed by device id, feeds two consumer groups with opposite scaling semantics — one shards for durability, the other broadcasts for fan-out. This contrast is the reason the pipeline looks the way it does.

07 — Read this before extending it

Known trade-offs

By design, documented on purpose — not oversights waiting to be found.

CPU is a proxy, not a real percentage Android exposes no permission-free, root-free way to read true system CPU load. The mobile app measures JS-thread timer overshoot instead — a genuine measurement, but of thread contention, not CPU%.
Every websocket instance eats the full topic Dashboard fan-out has no per-device Kafka subscription, so every horizontally-scaled apps/websocket instance consumes 100% of the topic regardless of local viewer count — the same cost Redis pub/sub already had.
Redis and ClickHouse are wired but idle Both keep their docker-compose service, config, and package — ready if a future use case (caching, analytics) needs them — but neither is on the metrics pipeline today.
Scoped RBAC is an "initial impl" A global role/permission catalog (not per-tenant); route-convention scope resolution rather than a fully generic resolver; scope_id is application-validated, not a DB-level constraint.

08 — Try it

Get the desktop app

A standalone Electron app that reports the local machine's own system metrics (CPU, memory, disk, uptime) — separate from the mobile device-monitoring pipeline above. Direct-download installers only, no app store; macOS isn't packaged yet.

Windows

  1. Download System Monitor-Setup-win.exe
  2. Run the installer and follow the setup wizard.
  3. The installer isn't code-signed yet, so SmartScreen may warn about an unknown publisher — choose More info → Run anyway to continue.
